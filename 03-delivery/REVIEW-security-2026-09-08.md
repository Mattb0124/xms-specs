# Security Review: XMS backend and frontend

**Date:** 2026-09-08
**Reviewer:** independent read of `xms-backend` @ `b7adcee` (plus the uncommitted `0025_finance_delivery` work) and `xms-frontend` @ `2f4c969` (plus uncommitted Axel and integrations work)
**Reviewed against:** `01-architecture/SECURITY-AND-TENANCY.md`, `01-architecture/DATA-MODEL.md`, `01-architecture/AUDIT-AND-ANALYTICS.md`, `01-architecture/INTEGRATION-PATTERNS.md`
**Scope:** tenant isolation, authentication and authorisation, secrets, injection and input handling, outbound request safety, audit and integrity, rate limiting and headers, and the web client.

---

## Summary

This is a genuinely security-first codebase and it is unusual to review one this disciplined at this stage. The isolation mechanics are real, not aspirational: `sys.apply_account_isolation` installs `ENABLE` plus `FORCE ROW LEVEL SECURITY` with matching `USING` and `WITH CHECK` on every account-scoped table it is handed, `withSession` is the single place that sets `xms.account_ids`, the binding is derived from the `Principal` and never from a request body, and a generated suite introspects `pg_class` and `pg_policies` so a new table cannot quietly skip the block. One guard resolves identity once, `authorizedParties` is checked, the long-lived agents audience is fenced to opted-in routes, API keys use a unique lookup hash plus bcrypt confirmation, the global `ValidationPipe` is actually registered with `whitelist` and `forbidNonWhitelisted`, and every route carries a declared permission enforced by a startup check and a golden snapshot. SQL injection is, as far as I can find, structurally closed: I traced every dynamic query builder and every one takes its columns from a fixed allowlist and its values from `$n` placeholders, with `ORDER BY` reduced to a closed ternary. CSV exports neutralise the full leading-character set and quote correctly, in all three places. The frontend has zero HTML-injection sinks, no cookie auth (so no CSRF surface), and telemetry that carries ids and enums rather than content.

The problems that matter fall into two groups. The first is a set of controls that are wired up but disconnected, and report success while doing nothing: revoking an API client does not pause its webhook subscriptions, because that write runs on a connection with no account binding where the RLS predicate is false for every row; and the usage-stream integrity digest and its S3 archive are computed on an unbound connection too, so they attest and export only the small minority of rows that carry no account. The isolation suite that the architecture nominates as the proof of TM-01 belongs to the same family: it was red for part of this review (a missing fixture for the in-flight `acct.finance_destinations` failed setup and silently *skipped* all 624 assertions), and it went green again because a concurrent build fixed the fixture, not because any gate demanded it. There is no CI workflow in any of the three repositories. The second group is outbound HTTP. The SSRF guard is thoughtful but checks the hostname as a string and is never re-applied after a redirect, and `fetch` is left on its default `redirect: 'follow'`, so a webhook receiver can bounce the signed POST into the VPC; while the ServiceNow connector's `base_url` is subject to no host guard at all and explicitly permits plain `http`. Separately, the guard derives the request realm from the token type rather than the user record, so a harness-minted token bearing a portal user's email produces an internal-realm principal on the `xms_app` role.

None of this is reachable by an anonymous internet caller today, and nothing I found leaks one account's data to another in the code as it stands. My overall judgement: the architecture is sound and the implementation is competent, but a short list of disconnected controls and outbound-request gaps should close before any client data lands, and the missing CI is the reason the first of them went unnoticed.

## Done right (please do not re-litigate)

These were checked and are correct; a future reviewer should spend their time elsewhere.

**SQL injection is structurally closed.** Not a single attacker-controllable interpolation was found across the tree. `quoteIdent` (`repository.base.ts:86-91`) allowlists `/^[a-z_][a-z0-9_]*$/` and *throws* rather than escaping. `conditions.ts` is a textbook allowlist translator: columns from a fixed `FIELDS` map, operators gated per column kind, UUIDs and enums pattern-checked, `MAX_CONDITIONS = 20` and `MAX_LIST = 50`, LIKE metacharacters escaped, and every value through `bind()`. `audit-search.ts` applies the same discipline to the audit grammar. `tickets.repository.ts:212-217` reduces `ORDER BY` to a closed ternary over three literals, so dynamic-`ORDER BY` injection is structurally impossible, and `views.ts:219` validates `sort` at write time as well. Saved-view `definition.columns` is stored and size-capped but never reaches a `SELECT` list. Dynamic table names are closed ternaries (`connectors.repository.ts:219-221`, `integrity.module.ts:294,327`, `sla-jobs.ts` module-level predicate constants). Every `WHERE` builder pushes `$n`. Full-text search is `plainto_tsquery('english', $n)` throughout; no `to_tsquery` string building.

**Isolation mechanics.** `sys.apply_account_isolation` (`0003:12-37`) is the single installer and applies `ENABLE` plus `FORCE ROW LEVEL SECURITY`, an operator policy with both `USING` and `WITH CHECK`, and either a portal policy with a `SELECT` grant or an explicit `REVOKE ALL ... FROM xms_portal`. `sys.account_ids()` returns `'{}'` when the setting is absent (`0001:49-52`), so an unbound connection sees nothing rather than everything. The hand-written policies on `acct.solution_articles`, `acct.article_versions`, `acct.article_feedback`, `rpt.usage_events` and `rpt.daily_snapshots` all carry `enable` plus `force` and were individually verified. The `SECURITY DEFINER` functions are minimal and correct: `sys.row_exists` pattern-checks `^acct\.[a-z_]+$` before `format`, `sys.account_for_alias` returns only an account id, `sys.csat_survey_account` returns only an account id, and all three are revoked from `public` with explicit grants.

**The isolation suite's design.** `test/isolation/isolation.int-spec.ts` introspects `pg_class.relrowsecurity`/`relforcerowsecurity` and `pg_policies` at runtime, cross-checks that list against a static scan of the migration files so a table cannot appear in neither, and proves read, write, insert and portal behaviour per table using the real database roles. 69 account-scoped tables are enumerated. The design is right; only its current red state (finding 3) is a problem.

**One guard, one resolution.** `AuthGuard.canActivate` (`auth.guard.ts:57-123`) checks bearer, verifies once, resolves the principal, checks realm, checks permission, in that order, writing exactly one security event per denial. `TokenVerifiers` verifies each token type exactly once, pins `RS256`, checks `issuer`, checks `azp` against `authorizedParties`, applies a 60-second skew, and (the part most implementations get wrong) refuses a Clerk session token carrying any `aud` other than the configured agents audience (`token-verifier.ts:126-130`), so a template token cannot be smuggled onto a normal route.

**Binding is derived, never supplied.** `bindingOf(principal)` is the only input to `withSession`; `assertUuid` rejects anything that is not a UUID before `set_config`; `SET LOCAL` plus an explicit reset on release means a pooled connection cannot carry a binding forward. Every service taking an `account_id` from a DTO or query string was checked and none escapes the binding: each runs inside a principal-bound transaction where `WITH CHECK` turns a foreign id into a `42501`, which `HttpExceptionFilter:54-55` maps to 404 rather than 403 so a foreign id is never confirmed. The two legitimate wideners (`runWithAccounts`, `portalWrite`) both refuse portal principals explicitly.

**CSV exports are correctly hardened.** `billing.ts:162-166` and `reporting.service.ts:258-263,350-354` neutralise the full leading set `= + - @ \t \r` with a `'` prefix *and* quote and double embedded `" , \n \r`. That is the complete treatment and it is identical in all three places; rows are CRLF-joined per RFC 4180. Every `Content-Disposition` filename is server-generated from timestamps and validated identifiers, and the one path taking a filename from the request strips `" \r \n`.

**Object storage keys are solid.** `assertObjectKey` allowlists `[A-Za-z0-9._\-/]{1,512}` and separately rejects `..` and a leading `/`, and it is called on every S3 operation. The local store adds a `resolve()` containment check. Account prefixes are derived from the loaded row under RLS, never from the request. Uploaded filenames are collapsed to `[^A-Za-z0-9._-] -> _` and truncated, behind a content-type by extension allowlist.

**Telemetry account handling.** `TelemetryController.ingest` (`telemetry.module.ts:274-283`) accepts a client-supplied `account_id` only when it is already in `principal.accountIds`, falls back to the portal principal's own account, and rejects otherwise. Attributes are reduced to scalars with a key allowlist and length caps; portal principals are restricted to five event types.

**Portal visibility.** Work notes, internal timelines and internal ticket fields are gated in the service by explicit `principal.kind === 'portal'` branches (`tickets.service.ts:223,258,959,1049-1051`), not only by the portal role's REVOKE, which matters because portal *writes* deliberately run on the `app` role (`unit-of-work.ts:42-47`, documented). `PortalService.assertVisible` enforces requester ownership by email unless `portal:view-org-tickets` is held.

**Email intake.** The alias resolves through `sys.account_for_alias`, a `SECURITY DEFINER` function returning only an account id (`0008:33-38`), and only then does the worker bind that single account (`email.service.ts:191`). Outbound mail cannot be header-injected: structured fields go to nodemailer's `MailComposer`, nothing is concatenated into a header, and every interpolated value in an email template is HTML-escaped with `branding.accent` validated against `/^#[0-9a-f]{6}$/i`.

**API keys.** Prefix plus unique-indexed SHA-256 lookup hash plus bcrypt confirmation (`principal.repository.ts:146-163`), so no O(n) bcrypt scan; the key is returned once and never stored in clear; expiry, revocation and `last_used_at` are checked or recorded; the projections that reach the API exclude `secret_hash`, `lookup_hash` and `secret_ciphertext`.

**The SNS signature check is genuine**, not decorative: certificate URL pinned to an AWS SNS host with a `.pem` path, certificate fetched, `crypto.verify` over the canonical `stringToSign`, and `SubscriptionConfirmation` deliberately not auto-confirmed. Finding 8 is the one thing it is missing.

**Regexes built from user input are escaped.** `redaction.ts:95` escapes the metacharacter set before `new RegExp`; the only other `new RegExp` calls read a static JSON file.

**Application baseline.** The global `ValidationPipe` really is registered with `whitelist`, `forbidNonWhitelisted` and `transform` with `enableImplicitConversion: false` (`main.ts:28-35`); the named AIX gap is closed. `helmet()` at `:24`, CORS pinned to `env.CORS_ORIGINS`, Swagger suppressed in production, `ParseUUIDPipe` used consistently on `:id` params. `pino` redacts `authorization`, `cookie`, `*.password`, `*.secret`, `*.token` and `*.api_key` by path, and the access line carries `request_id`, `principal_kind`, `user_id` and a reduced user-agent family, with no email, token or query string. `HttpExceptionFilter` returns codes and never a stack trace. `POST /v1/axel/suggestions/:id/decisions` looks under-permissioned in the route table but checks `decisionPermissionFor(suggestion.capability)` in the service (`suggestion.service.ts:262-277`); correct, just invisible in the snapshot.

**Frontend.** No `dangerouslySetInnerHTML`, no `innerHTML`, no markdown or HTML renderer anywhere; all user content renders as escaped JSX. `credentials: 'omit'` on every request, so CSRF is structurally absent. Zero `console.*` calls in application source. Only three `NEXT_PUBLIC_` variables, none secret. `frontend/scripts/check-next-config.mjs` fails the pipeline if `ignoreBuildErrors` or `ignoreDuringBuilds` ever appears, and `tsc --noEmit` is clean; the project's own "do not suppress type-check and lint errors" standard is enforced rather than merely stated. `frame-ancestors 'none'` plus `X-Frame-Options: DENY`, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`, `nosniff`, `poweredByHeader: false`. No rewrites or proxies; `images.unoptimized` so there is no optimizer SSRF. Attachments fail closed: downloads only through server-minted presigned URLs after an authorised read, quarantined files blocked with placeholder copy.

**Verification run for this review.** Backend `pnpm typecheck` clean, `pnpm lint` clean, `pnpm audit --audit-level=high` shows only the three known `image-size` advisories reached through `pptxgenjs` (the recorded exception). Frontend `tsc --noEmit` clean. The isolation suite was executed twice against a real PostgreSQL container: red on the first run and 624 of 624 green on the second, after concurrent work added the missing fixture (finding 3). Findings 1, 2 and 4 were each re-verified against the working tree as it stood at the end of the review.

## Open questions for the architecture owner

1. **Is the administrator's implicit all-account binding intended?** `admin:accounts` binds every live account and `admin:users` implies it (finding 21), which contradicts §3's "grants are explicit". Either the document or the code should move.
2. **What is the trust boundary with the harness?** `HARNESS_SESSION_SECRET` is symmetric and is used both to mint tokens *to* the harness and to accept tokens *from* it as any XMS user by email (finding 6). Is the harness inside the trust boundary to that degree, and should minting and accepting use different keys?
3. **Should `rate_cards`, `budget`, `contract position` and raw inbound email really sit behind `tickets:view`?** (finding 22). §3's catalog implies a commercial permission.
4. **What is the intended egress posture?** INTEGRATION-PATTERNS says outbound calls go through a NAT with a fixed egress IP. Do webhook, finance and connector calls all leave through an egress proxy that can enforce the destination allowlist centrally? That would be a better fix for findings 4 and 5 than per-call-site guards, and it would survive the next integration someone adds.
5. **Where does the tamper-evidence archive live?** §6 specifies a bucket with Object Lock in compliance mode plus Parquet and Glue; the implementation writes gzip to the single application bucket and keeps the chain in the same database as the events (finding 32). Is the locked bucket in the `xms-infra` backlog, and what is the interim story for an auditor?
6. **When does CI arrive, and what gates it?** There is no workflow in any of the three repositories. The isolation suite, the route-table snapshot, `pnpm audit` and the ZAP baseline named in §9 are all controls that only exist if something runs them. Finding 3 is the first instance of that gap producing a real regression, and findings 1 and 2 are the kind a per-control assertion would have caught.
7. **`session_replication_role = replica` in tests.** `test/csat.int-spec.ts:40-45` disables triggers to seed fixtures. Legitimate in a test, but it is the one construct that defeats the append-only guards, so it is worth confirming that no production role can `SET` it (it requires superuser, so this is a check rather than a concern) and that it never reaches a seed or a migration.
8. **Does the "dedicated" isolation tier have an owner?** `op.accounts.isolation_tier` exists in the data model as the escalation path for the pending Security ruling (§4), but `DbPools` resolves one connection string per role with no per-account resolution. If a client contract forces the dedicated tier, how much of the data layer changes?
