# Review: XMS web application, 2026-09-08

**Reviewer:** independent review pass (desk and portal, administrator, consultant and client)
**Scope:** `frontend` (xms-web) driven in a real browser against a locally seeded `backend` (xms-api and xms-worker)
**Stack under test:** backend at commit `a1d36b0` plus the working tree, frontend as of 2026-09-07, PostgreSQL 16 in `xms-postgres`, seed `pnpm seed:dev` (200 tickets, 2 accounts, 7 people, 6 articles)
**Related:** [WIREFRAMES](../01-architecture/WIREFRAMES.md), [USER-EXPERIENCE](../01-architecture/USER-EXPERIENCE.md), [DESIGN-SYSTEM](../01-architecture/DESIGN-SYSTEM.md), [TODO](./TODO.md)

---

## Summary

The build is much further along than a thirty-day plan would suggest, and the parts that work are genuinely good: the queue, the ticket record, the operations dashboard, the account record with its eleven tabs and the budget card are close to the v3 prototype, the fail-closed permission model is honest on every screen, the portal speaks client language throughout, there is not one em-dash anywhere, "generalization" is spelled with a z, focus rings are present on every control, and 532 API calls produced no 5xx at all with nothing slower than about 200 ms in steady state. What lets it down is a small number of defects that sit on the highest-traffic paths and that no unit test would catch, because each one only shows up when a person actually clicks. Three are severe: the All, Favourites and History finders in the navy bar crash the entire application, so the product's primary navigation device is unusable on every screen; the client portal's "My requests" list and most request detail pages return 404, so a client can raise a request and then never see it again; and every telemetry batch the browser sends is rejected by the API, so the usage dashboard has never received a single client event. A fourth, the invisible primary action button, is a one-line CSS cascade problem that hides the "New ticket" and "New article" labels on every list screen. Below those sit a set of fidelity gaps against the wireframes (no condition breadcrumb, no "Waiting on me" rail, a sidebar that scrolls off the page), a shipped seed that leaves the consultant with no permissions and the skills, billing, rate card, survey and demand screens entirely empty, and a desk that does not respond at narrow widths. None of these is architectural. All of them are a day or two of work, and the foundation underneath them is sound.

## What worked well

- **The permission model is honest.** Every desk screen fails closed with a specific, readable refusal that names the permission ("This screen needs the tickets:view permission"), and the sidebar and screen switcher shrink to match. The permission-less consultant saw 1 browsable screen; once granted, 13, with no Operations and no Admin. Nothing leaked.
- **Tenancy holds.** With a portal token, 24 desk routes returned `403 wrong_realm`, an Austral ticket key returned 404 to a Brookfield client, and the portal list, when it works, carried 29 Brookfield keys and zero Austral. The only desk-path 200s were the two notification routes, which are `@RealmOf('any')` by design and scoped to the caller.
- **The queue, the ticket record and Operations are close to the prototype**: navy finder bar, 44 px grey content header, no row striping, hairline rows with hover fill, mono keys and SLA values, 3px type bars, account identity dots, quiet P3 and P4 pills, the six-tab work area, the transition menu with "needs input" hints, the Solutions rail with matching articles and similar resolved tickets, the Contract card with burn and projection.
- **The account record is complete and well organized**: eleven tabs (Overview, Settings, Access, Calendars, Contracts, Budget, Billing, Report packs, Intake, Connectors, Configuration) in one consistent grammar with no bespoke admin chrome.
- **The budget card is the best screen in the product.** "9.3 h of 40 h used, 30.7 h remaining", threshold ticks with the next one named, "At the current rate of 1.2 h per business day the period ends at 87.5% of the budget; the budget runs out in 27 business days", and the unrated-minutes warning. It explains itself without a legend.
- **Portal copy is excellent.** "What do you need help with?", "Published solutions come first; open a request when you still need help.", "Leave it if you are not sure; the team will set it.", "You will get an email with the request key and every reply." Client language throughout, no jargon, no em-dashes.
- **Writes are coherent.** As a client I raised a request through `/portal/requests/new` and landed on `/portal/requests/CS1000203` with the key, status and details rendered. As a consultant I posted a work note and it appeared in the thread; the Time tab, quick-minute chips, after-hours checkbox and transition menu all behaved.
- **Focus states are everywhere**: a 2 px solid accent outline on all fourteen controls I tabbed through, with no missing rings.
- **No em-dashes anywhere** in source or rendered copy, and "generalization"/"Generalize" spelled with a z throughout.
- **The API is quiet and fast.** 532 requests, zero 5xx, zero error-level log lines, nothing above about 200 ms in steady state, consistent `{"code":"not_found","entity":...}` error shapes, and the connector circuit breaker tripped and reported correctly end to end.

## How to run this stack (exactly what I did)

Windows, Git Bash, from `C:\Users\matt.brown\Documents\repos\xms`.

```bash
# 1. Database (already running for me; this is the command)
cd backend && docker compose up -d
docker ps --format "table {{.Names}}\t{{.Status}}\t{{.Ports}}"   # expect xms-postgres healthy on 5433

# 2. Backend: build first, everything else runs from dist
cd backend
pnpm install                      # if node_modules is cold
pnpm build                        # nest build
node dist/db/migrate.js           # applied 13 of 25 migrations on my run
node dist/tools/seed-dev.js       # 167 tickets across BRK and AUS, 7 people, 6 articles, ~26 s

# 3. API on 3001. WEBHOOK_SECRETS_KEY is not in .env.example but the webhook
#    screens need it; passing it on the command line avoids editing .env.
WEBHOOK_SECRETS_KEY=local-webhook-secrets-key-0123456789 node dist/main.js

# 4. Worker. NOTE: it binds the same PORT as the API, so override it or you get
#    EADDRINUSE (finding 17).
PORT=3011 WEBHOOK_SECRETS_KEY=local-webhook-secrets-key-0123456789 node dist/worker/main.js

# 5. Tokens (12 h, HS256 against AUTH_DEV_SECRET)
node dist/tools/dev-token.js --email admin@example.test                            # administrator
node dist/tools/dev-token.js --email ana.costa@example.test                         # consultant
node dist/tools/dev-token.js --email pat.client@brookfield.test --org brookfield    # portal client
node dist/tools/dev-token.js --email sam.owner@brookfield.test --org brookfield     # portal account admin

# 6. The seed does not grant accounts (finding 5). Without this the consultant
#    has zero permissions and every desk screen refuses.
docker exec xms-postgres psql -U xms_migrator -d xms -c "insert into op.account_grants (user_id, account_id, granted_by) select u.id, a.id, u.id from op.users u cross join op.accounts a where u.email in ('ana.costa@example.test','erin.walsh@example.test','dev.patel@example.test','femi.adeyemi@example.test') and a.key in ('BRK','AUS') on conflict do nothing"

# 7. Frontend
cd ../frontend
pnpm install                      # if cold
pnpm dev                          # http://localhost:3000, ready in ~10 s
```

Sign in at `http://localhost:3000/dev/sign-in` and paste a token, or set it directly:

```js
localStorage.setItem("xms.devToken", "<token>")
```

`.env.local` needs only:

```
NEXT_PUBLIC_API_BASE_URL=http://localhost:3001
NEXT_PUBLIC_AUTH_DEV_MODE=true
```
